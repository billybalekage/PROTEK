PROTECK — BACKEND ENGINEERING & SECURITY SPECIFICATIONS (server/)Version : 1.0Stack Technologique : 100% JavaScript (Vanilla JS / Node.js) — Pas de TypeScriptArchitecture : Clean Architecture1. OBJECTIFS ET PRINCIPE DIRECTEURLe dossier server/ héberge le cœur de calcul normatif (NF C 15-100 / CEI 60364) et la logique applicative de PROTECK. La sécurité, la résilience face aux réseaux instables (ex: RDC) et l'immutabilité des règles d'ingénierie sont nos priorités absolues.2. ARCHITECTURE DES DOSSIERS (CLEAN ARCHITECTURE)Le backend est strictement cloisonné pour séparer les règles métiers pures des mécanismes d'infrastructure (HTTP, persistance, etc.) :server/
├── src/
│   ├── core/                  <-- [Règles Métier Pures] Algorithmes de dimensionnement NF C 15-100 (100% testables, sans I/O)
│   ├── use-cases/             <-- [Cas d'Usage / Application] Orchestre les flux de données entre les adaptateurs et le core
│   ├── adapters/              <-- [Interface / Contrôleurs] Routeurs HTTP, gestionnaires de requêtes/réponses
│   └── infrastructure/        <-- [Système] Configuration du serveur, base de données, middlewares de sécurité
├── tests/                     <-- Tests unitaires obligatoires (Vitest / Jest) ciblant le dossier core/
└── SERVER.md                  <-- Documentation des normes backend
3. RÈGLES DE SÉCURITÉ ET BONNES PRATIQUES BACKEND3.1. Immutabilité et Pureté du Cœur de Calcul (server/src/core/)Fonctions pures (Pure Functions) : Le dossier core/ ne doit jamais contenir d'effets de bord, d'appels asynchrones, de requêtes de base de données ou d'accès au système de fichiers. Une même entrée doit toujours retourner strictement le même résultat mathématique ou normatif.Validation stricte des types en JavaScript pur : Étant donné l'absence de TypeScript, chaque fonction du core doit valider de force les types de ses paramètres d'entrée (ex: vérifier que $P$, $L$, et $U$ sont des nombres finis, positifs et non nuls) avant d'exécuter les calculs.3.2. Robustesse et Gestion des Erreurs (Contexte de Réseaux Instables)Pas de plantage global (Crash Prevention) : Chaque adaptateur HTTP ou contrôleur doit envelopper l'exécution des cas d'usage dans des blocs try/catch stricts.Codes d'erreur normalisés : En cas d'échec de calcul (ex: section de câble introuvable, dépassement des limites normatives), le serveur retourne une réponse JSON normalisée et prévisible :{
  "success": false,
  "error": {
    "code": "ERR_CALC_INVALID_RANGE",
    "message": "La puissance saisie dépasse les limites admissibles pour la section sélectionnée."
  }
}
Garde-fous (Guards) : Protection systématique contre les divisions par zéro, les boucles infinies dans les recherches itératives de tables, et les valeurs aberrantes.3.3. Sécurité de l'API et EndpointsEn-têtes HTTP sécurisés : Utilisation systématique de middlewares de type Helmet pour masquer l'empreinte du serveur et prémunir l'application contre les attaques courantes (XSS, clickjacking).Validation des charges utiles (Payload Validation) : Limitation de la taille des requêtes JSON entrantes pour prévenir les attaques par déni de service (DoS) via des structures de projets électriques volumineuses.Rate Limiting : Protection des routes de calcul intensif contre le spam ou les requêtes abusives.3.4. Gestion de la ConfigurationVariables d'environnement : Utilisation obligatoire d'un fichier .env pour stocker les configurations sensibles. Aucune donnée secrète ou paramètre de déploiement ne doit figurer en dur dans le code source.Journalisation (Logging) : Traçabilité des erreurs critiques et des anomalies de calcul via un logger structuré, en veillant à ne jamais logger de données personnelles ou sensibles.
